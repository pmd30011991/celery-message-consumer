<objective>
Align PREFETCH_COUNT with pool concurrency so RabbitMQ stops delivering new messages when the pool is full, preventing unbounded in-memory message accumulation.

Purpose: After Phase 1's async dispatch fix, the listener eagerly drains messages from the broker. With PREFETCH_COUNT=1 (current hardcoded value), the pool can never process more than one message concurrently -- defeating the entire point of the pool. Setting prefetch_count to pool.limit enables true concurrent processing while letting the broker enforce backpressure.

Output: Modified settings.py, modified handlers.py, new test_backpressure.py
</objective>

**handlers.py changes:**

1. In `AMQPRetryConsumerStep.start(self, c)`, after `self.pool = c.pool`, add:
```python
pool_limit = getattr(self.pool, 'limit', None)
# Explicit setting wins; fall back to pool concurrency; final fallback = 1
self.prefetch_count = settings.PREFETCH_COUNT or pool_limit or 1
```
This works because settings.PREFETCH_COUNT=0 is falsy, so `or pool_limit` kicks in. If pool_limit is also None/0, `or 1` catches it. If settings.PREFETCH_COUNT is explicitly set to e.g. 5, it's truthy and wins.
